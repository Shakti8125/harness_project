### Failure 1 — dependency conflict (FIXED, committed in `57f33bb`)

The first build died in `pip install -r requirements.txt gradio[oauth,mcp]==6.26.0`.
Reproduced locally with `uv pip compile`:

```
gradio 6.26.0 depends on pydantic>=2.11.10,<=2.12.5
you require pydantic==2.13.5
-> No solution found when resolving dependencies
```

Cause: `requirements.txt` had been generated by `uv export`, i.e. exact pins for the whole
transitive set. A Space installs **its own** gradio over the top, and gradio constrains
packages this project also depends on, so a fully pinned set cannot co-resolve by
construction.

Fix (already applied): `requirements.txt` now lists only the **direct** dependencies from
`pyproject.toml`, unpinned, and lets pip resolve the overlap. `pyproject.toml` + `uv.lock`
remain the source of truth for the project, the Docker image and CI.

Consequence, verified rather than assumed: the Space resolves **pydantic 2.12.5** and
**starlette 1.6.0** where the lock gives 2.13.5 / newer. The suite was run against those
exact versions — `uv run --with "pydantic==2.12.5" --with "starlette==1.6.0" pytest -q` →
**253 passed**. Re-run that check if `requirements.txt` or `sdk_version` changes.

### Failure 2 — the open one: port bind conflict

The build now **succeeds**. The app then fails at startup:

```
===== Application Startup at 2026-09-07 20:39:47 =====
INFO:     Started server process [1]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
ERROR:    [Errno 98] error while attempting to bind on address ('0.0.0.0', 7860):
          [errno 98] address already in use
INFO:     Waiting for application shutdown.
INFO:     Application shutdown complete.
```

(The block repeats — the platform retries once.) Note the ordering: uvicorn runs the
lifespan **then** binds, so "Application startup complete" followed by a bind failure is
one uvicorn instance losing the port to something that already holds it.

`app.py` currently ends with:

```python
if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=SPACE_PORT)   # SPACE_PORT = 7860
```

This bypasses gradio's own launcher, which on a Space is what coordinates with the
platform (port selection, the queue, and — on ZeroGPU — the `spaces` supervisor).

The Space was created on **ZeroGPU**, not free CPU. That is why the build installs
`spaces==0.51.3` (visible in the build log) — a stack this application has no use for.

## 4. Proposed change

**Scope: `app.py` only. ~30 lines. No change to `src/**`, no change to tests, no contract
change.** The Docker path is untouched, so `docker compose` and any container host keep
working exactly as they do now.

1. **Remove** the `if __name__ == "__main__": uvicorn.run(...)` block and let gradio's
   `demo.launch()` own the port. That is the canonical Gradio Space entrypoint and the only
   thing that cooperates with the platform's port arrangements.
2. **Mount the FastAPI app onto gradio's app after launch**, so `/healthz`, `/v1/runs`,
   `/v1/replay/{scenario}` and `/v1/runs/{id}/trace` still resolve. Sketch:

   ```python
   demo.launch(prevent_thread_lock=True)   # gradio binds, platform-aware
   demo.app.mount("/", api)                # unmatched paths fall through to the API
   demo.block_thread()
   ```

   Mount order works because Starlette resolves routes per request: gradio's own routes are
   registered first and win, and `/healthz` / `/v1/*` — which gradio does not define — reach
   the mounted app.

3. **Call `recorder.initialize()` explicitly.** This is the easy-to-miss part. A sub-app
   mounted with `Mount` does **not** receive Starlette lifespan events, so
   `src/api/main.py`'s `lifespan` will no longer run. Without it the `spans` table is never
   created: span writes are swallowed (`TraceRecorder._persist` catches and logs, by
   design — tracing must never fail a run) and `GET /v1/runs/{id}/trace` returns 404 or
   errors. Get the recorder from `src.api.deps.get_app_context()`.

4. If the mount-at-`/` approach fights gradio's own catch-all routes, the fallback is to
   mount at a prefix (`/api`) and accept that the public paths differ from the local ones —
   worth noting in `docs/deploy-huggingface.md` if it comes to that, because the Verify
   block's curl commands would then differ between local and deployed.

### Time and risk

- Edit + local verification: ~15 minutes.
- Local green does **not** imply remote green — the supervisor cannot be reproduced locally.
- Each deploy iteration is ~3–4 minutes (build + poll). Budget **1–3 iterations**, so
  **20–45 minutes** wall clock, mostly waiting.
- **A risk no code change can remove:** ZeroGPU is a Pro tier and the Space reports
  `hardware: current=None`. If the platform never allocates hardware, the Space may not
  serve regardless of how `app.py` is written. If iteration 1 shows the app binding
  successfully but the URL still not responding, this is the likely reason and the honest
  answer is to stop and record step 5 as blocked on account tier.

### The alternative worth taking seriously

Record step 5 as blocked-on-hosting, close Phase 1, and move on. Everything step 5 was
meant to demonstrate is already proven: the container builds, boots, serves and diagnoses
correctly (`docker compose` + all four other Verify steps). Step 5 is the "publicly
reachable" checkbox, and it is now gated by a hosting account tier, not by the build.
**Phase 2 does not depend on it.** Deployment can be revisited with a card, a Pro account,
or a different host (Render, Koyeb, a VPS, or a Cloudflare quick tunnel for a live demo).
