## Wave 3 fixes

Four findings routed to `api-surface` by the Wave 3 audit (`docs/progress/phase-0/review.md`),
all fixed. Territory unchanged: only `src/settings.py`, `src/api/main.py`, `Dockerfile`,
`pyproject.toml`, and this file were touched.

### Finding 5 [MEDIUM] — mistyped `.env` key printed its raw secret into the boot log

`src/settings.py`: `get_settings()` now wraps `Settings()` in `try/except ValidationError`
and re-raises a new `SettingsError` built by `_redact_validation_error()`, which walks
`exc.errors(include_url=False)` and emits only `loc` (field/variable *name*) and `type`
(error kind) per problem — `err["input"]`, which is where pydantic puts the raw offending
value, is never read. The re-raise uses `raise ... from None` so Python's default
traceback formatter does not chain-print the original `ValidationError` (whose `__repr__`
does embed `input_value`). `main.py`'s existing import-time `get_settings()` call
therefore now surfaces a clean, secret-free message at boot.

One nuance: our own new `model_validator` (finding 6, below) also raises through this
path via pydantic's "value_error" wrapping. Since *that* message is authored by us and
already values-withheld, `_redact_validation_error` special-cases `type == "value_error"`
to surface the full `msg` (still safe) rather than collapsing it to a bare type code —
otherwise the unrecognised-env-var error would be useless to an operator.

### Finding 6 [MEDIUM] — `extra="forbid"` doesn't catch env-var typos from the real process environment

Implemented the validator (not the PLAN.md amendment). Added
`Settings._no_unrecognised_harness_env_vars`, a `model_validator(mode="after")` that scans
`os.environ` for `HARNESS_`-prefixed keys not matching any field's expected env-var name
(`{env_prefix}{FIELD_NAME}`, case-insensitive) and raises `ValueError` naming only the
unrecognised variable *names*, never their values. This closes the gap pydantic-settings
leaves open (it only enforces `extra="forbid"` against the `.env` *file* source, not the
real environment that Docker/Fly use), delivering the guarantee PLAN.md:1770 already
promises rather than weakening the promise. `os.environ` access lives entirely inside
`src/settings.py`, so `tests/unit/test_no_env_access.py` (which excludes `settings.py` by
design) is unaffected — confirmed by re-running it (30 passed).

### Finding 9 [LOW] — image has no fixtures, so the Phase 1 demo path can't run in the container

Added `COPY fixtures ./fixtures` to the Dockerfile's runtime stage (after the existing
`COPY --from=builder ... /app/src`, before the `chown -R harness:harness /app` that now
also covers it). `.dockerignore` already excluded only `fixtures/recorded/`, so the rest
of the build context's `fixtures/` tree (53 KB, `scenarios/real_regression/**`) ships as-is
— no change to `docker-compose.yml` needed since fixtures are baked into the image at
build time, not volume-mounted. Verified live inside the running container (see Commands
run): `/app/fixtures/scenarios/real_regression/{scenario.yaml,webhook.json,api/,logs/}` all
present.

### Finding 10 [LOW] — `/healthz` reports the wrong degraded value and a hardcoded `status`

`_db_reachable()` now returns a three-way string (`"ok" | "degraded" | "error"`) instead of
`bool`: `sqlite3.OperationalError` whose message contains `disk i/o error` (case-insensitive)
maps to `"degraded"` per PLAN.md B.3's disk-full row; any other exception maps to `"error"`.
`healthz()` sets `"db"` to that value directly and sets `"status"` to `"ok"` only when
`db == "ok"`, otherwise mirroring the db value — so a degraded/errored db is no longer
papered over by a hardcoded `"status": "ok"`. The healthy-path body is unchanged and was
re-verified byte-for-byte: `{"status":"ok","db":"ok","version":"0.1.0"}`. The degraded/error
paths could not be exercised end-to-end against a real disk-full condition in this
environment (would require an actual I/O failure injection); the mapping logic itself was
sanity-checked by unit-level reasoning against the exact `sqlite3.OperationalError` message
strings SQLite emits for `disk I/O error`, matching PLAN.md B.3's literal wording.

### Notes for the reviewer

- The `model_validator` only runs after all field-level validation succeeds (pydantic
  semantics), so a `.env`/env combination that has *both* a missing required field *and*
  an unrecognised extra variable reports only the missing-field error, not the
  unrecognised-variable one, in that single run — demonstrated above (container case with
  `HARNESS_GITHUBTOKEN` set: reports `github_token: missing`, not the extra-var message).
  This does not weaken the guarantee (the process still fails closed either way, and fixing
  the reported error and re-running will surface the next one), but a reviewer scripting
  against the exact error text should not assume all problems are reported in one shot.
- `"degraded"` (finding 10) could not be exercised against a genuine disk-I/O failure in
  this environment; the string-match on `sqlite3.OperationalError`'s message is the
  mechanism available at Phase 0 (no schema, no dedicated disk-full simulation harness
  yet) and should be revisited once Phase 3's SQLite failure-injection tests exist.
