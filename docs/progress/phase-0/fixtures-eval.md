## Summary

Phase 0 scope only: the fixture directory format (documented in `fixtures/README.md`) and
the `real_regression` skeleton under `fixtures/scenarios/real_regression/`. No `scripts/`
were added — nothing was strictly necessary this phase (no `replay.py`/`eval.py` yet to
support, per the brief). No other scenario directories were created.

Format decisions, and why:

- **`get_job_logs` has no `api/` recording.** GitHub's real endpoint returns raw text (a 302
  to blob storage), and the raw bytes already live at `logs/job_<id>.txt`. Storing the same
  multi-thousand-line content a second time inside an escaped JSON string in `api/` would
  give the fixture two copies of the truth that could silently diverge — exactly the
  consistency risk the skill file warns about. `ReplayToolGateway.get_job_logs` is expected
  to read `logs/job_<id>.txt` directly (truncating to `max_bytes` if given) and treat a
  missing file as the tool-error path. I documented this explicitly in `fixtures/README.md`
  so `gateway_replay.py` (harness-core/cicd-integration territory) is written against a
  stated contract instead of guessing.
- **`api/` filenames encode the real GitHub REST path**, not the internal tool name, so that
  a future `record_fixture.py` capture is a mechanical dump of `METHOD + URL path` rather
  than a hand-written transform. `compare/BASE...HEAD`'s `...` becomes a single `-` (three
  literal dots in a filename is legal on Windows/NTFS here but needless noise); documented
  with a worked-example table keyed to the actual CI/CD tool catalog (PLAN.md lines
  1170–1186).
- **`scenario.yaml` fields are all optional except `name`, `description`, `expected.category`
  and `expected.min_confidence`.** The skill file and the brief both flag that an
  over-specified label makes `scripts/eval.py` a flaky gate later; I only filled in
  `commit`, `cites_any_of`, `action`, `effect`, `baseline_kind`, `cold_start` for
  `real_regression` because this scenario's design genuinely determines all of them (single
  clean commit, exactly one plausible action/effect pair, a real branch-green baseline, not
  a cold start).
- **No secrets, and no real personal data.** The commit author/committer in
  `webhook.json`/the compare recording is a fictitious `Jordan Lee
  <jordan@harness-demo-repo.example>`, not any real person — PLAN.md states this repo is
  meant to go public, so fixture data should not carry anyone's real identity even for
  flavor.

## Wave 3 fixes (audit findings 7 and 8)

The Wave 3 audit (`docs/progress/phase-0/review.md`) confirmed `real_regression`'s
id-consistency sound by hand, confirmed zero secrets in `fixtures/`, and ruled the
`get_job_logs`-has-no-`api/`-file design sound. It found two narrower defects in my own
output, both fixed here.

### Finding 7 — `scenario.yaml`'s label was internally unsatisfiable

`min_confidence: 0.75` with `effect: require_approval` was inconsistent with
`policy.yaml`'s `open-fix-pr` rule, which requires `diagnosis.final_confidence: {gte: 0.85}`
for `require_approval` to be the matching effect. A run scoring in `[0.75, 0.85)` clears the
label's own `min_confidence` bar but falls through every rule to `default_effect: deny` —
`min_confidence` passes, `effect` fails, on the *same* run. That is the flaky-gate shape
`fixtures/README.md`'s "only assert what the scenario genuinely determines" line exists to
prevent.

**Remedy chosen: raised `min_confidence` to `0.85`; kept `effect: require_approval`.**
Did not drop `effect`.

Reasoning:

- `effect: require_approval` is the single most demo-relevant claim this label makes —
  it's the fixture's whole reason to exist per `fixtures/README.md`'s own scenario table
  (`real_regression` → "correct blame + `require_approval`"). Dropping it to resolve the
  inconsistency would silence the assertion the scenario was built to prove, which is a
  worse outcome than tightening a number.
- Raising `min_confidence` to `0.85` does not contradict PLAN.md's Phase 1 Verify block
  (`PLAN.md:360`, `EXPECT ... conf:>=0.75`). `0.85 >= 0.75`, so any run that clears the
  eval label's stricter bound also clears the weaker one the manual `curl`/`jq` check in
  Phase 1 performs. Nothing in Phase 1's verify script is broken by this change; the
  eval label is simply a stricter, later-phase-appropriate bar than the smoke-test bar.
- This scenario is deliberately the "everything points at one clean cause" case: single
  commit, single-line diff, the exact failing assert quoted in the diff's own function —
  precisely PLAN.md's rubric row for `0.90-1.00`, "Deterministic match: the error string
  and the diff independently name the same cause" (PLAN.md line ~242). None of the
  negative confidence adjustments apply to it in the phases where it's actually scored
  against `effect` (Phase 2+, once guardrails exist): `baseline_kind: branch_green` (not
  `cold_start`), diff is non-empty (no `empty_diff_contradiction`), and citations are
  expected to be present (no `no_citations`). So `0.85` is a floor this scenario's own
  design should clear rather than a bar it merely hopes to clear — I'm not asserting a
  number I have reason to think is unreachable for this fixture.
- I weighed PLAN.md's Open Risk 4 ("confidence numbers are asserted, not measured") as a
  reason for caution, but concluded it argues for leaving *some* margin above the
  `open-fix-pr` threshold (which `0.85` — the threshold itself — does not do) rather than
  for abandoning the `effect` assertion altogether. If Phase 1/2's actual measured
  confidence for this fixture lands below `0.85` in practice, that is itself useful
  eval-harness signal (the model isn't as confident on the "cleanest possible" case as the
  rubric intends) and should be fixed by prompt/calibration tuning, not by quietly
  lowering the label back down.

Changed: `fixtures/scenarios/real_regression/scenario.yaml` — `expected.min_confidence:
0.75` → `0.85`, with an inline comment recording this reasoning and citing "Wave 3 audit
finding 7" so a future editor doesn't silently revert it.

### Finding 8 — README's `get_job_logs` contract didn't say which end `max_bytes` keeps

Added an explicit **"Truncation direction"** paragraph immediately after the existing
`get_job_logs` design-decision paragraph in `fixtures/README.md`. Exact wording added:

> **Truncation direction — `max_bytes` keeps the LAST `max_bytes`, never the first.** If a
> log exceeds `max_bytes`, the implementation must drop bytes off the *front*, not the back
> (i.e. `content[-max_bytes:]`, not `content[:max_bytes]` / `f.read(max_bytes)`). This
> mirrors PLAN.md:222's "Log download hard cap — 20 MB (keep the *last* 20 MB)": the
> proximate failure is near the end of a real Actions log (setup/install noise comes
> first, the failing step and its traceback come last), so keeping the head and
> discarding the tail throws away the one thing every scenario exists to test.
> Concretely: `real_regression`'s log is grown to several thousand lines with the
> `assert 91 == 90` anchor placed well before the end (per the realism requirements
> below) specifically so that a `get_job_logs` implementation which truncates from the
> wrong end fails this fixture loudly — `f.read(max_bytes)` on that log would return only
> runner bootstrap and pip-install output, the anchor would be gone, and the
> Diagnostician would have to guess `category: unknown` instead of citing real evidence.
> Get this backwards and the eval failure looks like a model/prompt problem when it is
> actually a one-line truncation bug.

This lives permanently in `fixtures/README.md` (not just the Phase 1 brief) per the
reviewer's instruction, so `gateway_replay.py`'s author has no reason to guess.
